# Design

- Frontend-only changes: finance-ui.js owns row markup, click handling and image loading; finance.css owns ledger and receipt-dialog layout; app.js skips generic illustration injection for the dedicated finance-image-dialog. Index/app resource versions updated together.
- Each row has purpose heading and kind/category capsules on one wrapping baseline, amount at the right, notes below, and one shared bottom footer: screenshot count link at left, edit/refund/delete at right. Actions use the same font size/line height as the screenshot link while retaining readable hit areas. Long titles/amounts must wrap safely at320px.
- No list image/thumbnail markup, observer, authorization or downloads. The sole screenshot link opens a dedicated preview with escaped purpose, kind/category, signed formatted amount and ledger civil date. No generic screenshot title, explanatory upload text or decorative illustration.
- Removing individual thumbnails must not hide additional receipts: provide accessible previous/next controls and current image count inside the preview for multi-image entries. Preview binds the clicked entry, not a globally shared receipt ID; preserve retry, request ownership, close/session replacement safety, one actual image fetch on demand and private URL validation.
- Existing data and APIs/storage paths remain untouched. Tests exercise no eager reads, entry-specific metadata, image navigation, stale/closed responses and real app modal decoration ownership. Browser fixture uses synthetic entries only.
- Follow-up boundary: remove only the ledger category filter markup/state/query binding and update the existing filter grid. Expand the shared finance-domain category recognizer used by client and server; retain unknown-purpose fallback, manual selection, inactive categories, custom category contracts and saved historical category IDs. No cloud AI or dependency. Add meaningful multi-category/ambiguous-purpose and backend integration coverage. Recheck all changed shared behavior before publishing.

- Follow-up compatibility: existing purpose-only custom categories with no keywords (e.g. 买菜) must not mask newly recognized built-in concrete intents for future automatic inference. Preserve exact custom keyword rules, unknown-purpose reuse, explicit categoryId and all historical entries/categories. The server automaticCategory must consult the shared matcher before its legacy named fallback. Test old purpose category + future automatic entry + explicit old selection together.

- Review edge case: built-in concrete intent also outranks substring matches from empty-keyword purpose-name categories (买东西买药→health, 超市买菜刀→shopping). Vague platform-only evidence must not override an existing purpose category such as 淘宝修鞋. A pre-upgrade successful write retried with categoryId empty after rule changes can safely conflict rather than return duplicate; redesigning cross-version create-hash identity is out of this UI/rule scope and no existing entry is overwritten.

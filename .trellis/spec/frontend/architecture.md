# Frontend Architecture

## Files and boundaries

- `shendu/public/index.html` provides body-sibling `#app`, `#rail-root`, `#modal-root`, and `#toast-root` containers and loads local component CSS, `styles.css`, and `app.js`. `app.js` imports the Vite-built shadcn React bridge from `public/ui/`; source components live under `shendu/ui/`. Follow [Component islands](./component-islands.md) for ownership and build contracts.
- `shendu/public/app.js` owns route state, HTML templates, API calls, and event binding. `shell(content)` renders the shared top navigation and main area inside `#app`; `setRailOverlayOpen()` mounts the stage dialog separately in `#rail-root`. `navigate(route)` selects the view.
- `shendu/public/styles.css` owns global tokens, page styles, and breakpoints. Local fonts live under `shendu/public/assets/fonts/`.
- `public/history-archive.css` and `public/workspace-pages.css` load after the shared stylesheet and own only the archive and personal-space presentation. Keep their selectors scoped to `.history-page`, `.workspace-page`, `.workspace-dialog` or the explicitly listed operation-form IDs; they must not restyle overview, review canvases, action verification or stage/calendar.

## Render and bind

Page functions return HTML strings. `renderMarkup()` cleans old component roots and synchronously enhances new controls before listeners bind. `renderReview()` calls `shell(content)` then `bindReview()`; `shell()` calls `bindCommon()`. A rerender removes old listeners, so every new control needs a binding path. Complex dialogs, menus, Tabs and calendars use explicit surface helpers; remove duplicate legacy keyboard/focus owners.

The six review types share `TYPES`, `QUESTIONS`, and `renderReview()`. Daily content is split into `dailyEvidence()`, `dailyReflection()`, `dailyActionFields()`, and `dailyJournal()` in `app.js`; the other five use `extendedReviewHtml()` and `EXTENDED_FLOW` from `extended-flow.js`. Both branches reuse the art canvas, answer disclosures and calendar, while preserving separate prompt state. Extend shared code for common behavior and the relevant flow branch for type-specific behavior.

Daily review groups questions under `DAILY_STEPS` from `daily-flow.js`; `dailyPrompts(metricCount)` defines the actual screen order. `state.dailySection` tracks the01—04 group and `state.dailyPrompt` the current question (`sleep`, `energy`, `metric-N`, `risk`, `today`, `cause`, `action`, `ifCondition` (paired obstacle/response), `verifyDate`, `journal`). `dailyReviewHtml()` mounts all fields once; `showDailyPrompt()` changes `hidden` without replacing input nodes. `dailyPromptOwner(field)` maps ifThen to the combined ifCondition screen for traversal, redraw and exact-field error focus; both original inputs/payload keys remain mounted together. Use `dailyPromptIssues()` for current-question checks, `dailyStepIssues()` for final completion and `showDailyIssues()` to expose/focus the exact missing question. Evidence/cause/journal remain optional. `renderReview()` preservation options keep prompt/section/dirty through add/remove, save and completion. A first save changes null ID to a real ID and must not reset the flow. True record entry starts at intro; hidden questions still have values and participate in final validation.

The other five types use `state.extendedPrompt` and `extendedPrompts(type,QUESTIONS[type])` for their own question order. `extendedReviewHtml()` mounts every input once; `showExtendedPrompt()` changes hidden state, stage label, art phase, side and focus. `extendedPromptIssues()` validates only the visible question; `extendedReviewIssues()` provides the final client check. `ifCondition` and `ifThen` share the `ifThen` screen, but remain separate stored fields. The 16 semantic `data-review-phase` slugs are stable art replacement slots; each slot now loads its distinct generated `assets/extended/<phase>.webp`, with PNG sources, prompts and SHA256 in the same directory. Cache revisions change when assets are replaced, without changing questions or payload. See [Extended review flows](./extended-review-flow.md) for exact contracts.

All answer rows use `dailyAnswerInputs()` around the shared `answerItemRow()` / `answerAddButton()` markup. Native details keep all textareas mounted; `dailyAnswerPreview()` is escaped on render and assigned with textContent on edits. `openDailyAnswer()` / `focusDailyAnswer()` reveal one target before sizing/focus after add, remove or validation. Toggle alone does not mark dirty or save. The five extended flows retain their own original question keys and action fields.

Daily uses a full art canvas for both intro and writing. `.daily-flow.daily-art-flow[data-daily-scene][data-daily-side][data-daily-current-prompt]` is the visual scene owner; its single `.daily-scene-art` contains the local transparent1254-square WebP `.daily-scene-image` variants generated with built-in imagegen; source PNG/prompt/manifest remain in assets/daily. The container is decorative, aria-hidden and pointer-inert. Scene state derives only from the current prompt; its side follows the real01—04group (right/left/right/left), never fabricated record content. `setDailyImmersive()` hides the shared shell header for all six review intros and writing views, while their own stage/date/exit controls remain visible; leaving a review restores the normal shell. Keep this exception local to the six review routes. The daily header no longer renders headerBrandContent() or the daily divider; it keeps its unique current-group node, date and exit. Shared normal-page branding stays owned by headerBrandContent() and its existing guarded navigation. `dailyIntroLines()` splits each review intro at Chinese comma/full-stop, preserving punctuation and full text. Each phrase contains the same daily-glyph spans. The template supplies --daily-intro-columns from the longest code-point count with tracking allowance; scoped>=821px container units cap text size to the actual copy column, while phones retain natural wrapping. showDailyPrompt keeps the unique daily-current-group in the mounted header without a logo; focus transitions scroll that header instead of scrolling the editor past it, with a nearest start-button fallback in intro. `startDailyTypewriter()`/`cancelDailyTypewriter()` own the intro effect, preserve full-text geometry/semantics and cancel work on departure/replacement.

`statsHtml()` is owned by the shared stage/calendar dialog and renders once inside `rightRail()`. Review bodies must not call it. Its compact three-stat controls navigate through the existing guard after closing the parent dialog.

`bindCalendar()` mounts the stage dialog's real shadcn/DayPicker Calendar, preserving its original first-matching-record date lookup and draft/completed/verified/today presentation. Keep disabled-date rules, six week rows, descriptive buttons and view-only month controls; DayPicker owns keyboard and month transitions. The centered `.stage-folio` Dialog uses Tabs for calendar/stage/pending with shared statistics in its footer; force-mounted inactive panels are hidden rather than discarded. There are no side-category cards or decoration templates. `ui/stage.css` owns the isolated folio/calendar layout instead of legacy `.right-rail` geometry. This calendar remains separate from the verifyDate form calendar.

`renderHistory()` owns the illustrated archive page, including its local q/type/year/month filter projection and post-render search-caret restoration. Cards retain `data-open-record` and `bindRecordOpen()`, so the original ID decides which stored record opens. Existing local category art is decorative and has no persisted selection field; escape every title/excerpt/period/status passed into HTML. Keep history-only markup/styles scoped away from the approved overview and immersive review canvases.

`WORKSPACE_SCENES`, `workspaceArt(scene,className)` and `workspaceDialogHead(title,description,scene)` reuse reviewed local record illustrations for backup, users and settings/account dialogs. The dialog helper preserves `.modal-head h2/p` for the existing title/description extraction and settings-back navigation. `renderBackup()` inserts its asynchronous content with `renderMarkup()`; controls inserted after `bindCommon()` need their own local listeners. Its failure branch binds `#backup-retry` directly to `renderBackup()`. Do not rely on a late `data-nav` attribute or rebind every shell listener to repair one inserted control.

`record-art.js` owns the local archive/action image catalog and `recordArtAssignments(records,catalog=RECORD_ART) -> Map<id,{src,scene}>`. Both list views must pass the complete `state.records` before filtering or status partitioning; assigning on the visible subset would change the picture on search or page switches. The allocator sorts a copy by period/ID, keeps each category in its own palette, exhausts the least-used pool before reusing a picture, then uses local keywords and a stable ID hash to choose. No generated path may be registered before its file exists and passes visual review. The catalog now has65 reviewed independent scenes in `assets/records/`: daily30, weekly7, monthly12, quarterly4, yearly6, decision6. That directory's manifest binds published WebP and original PNG hashes; source PNGs/contact sheets/gallery live in `output/imagegen/record-library/`, with prompts and hash-bound visual approval in `art/record-library/`. Requested image size and actual source dimensions are recorded separately. No record schema, external content transmission, overview artwork or review-canvas changes.

Routes are in-memory names such as `overview`, `daily`, `history`, `actions`, and `backup`. `boot()` opens `overview` after `refreshData()`. `renderOverview()` is the overview-only page; other page bodies retain their own render functions. `attemptNavigate()` guards unsaved input before moving between routes. Header, calendar, overview cards, and record-card handlers use that guard. Preserve it when adding navigation affordances.

`review-navigation.js` owns one review visit's transient return context through `createReviewNavigator({source,guard,open,restore})`. App entry paths use `enterReview()` before changing `state.route`; the controller captures a valid list/source route, document scroll and original record ID only when the existing guard allows entry. Both daily/extended exit handlers call its `exit()`, with the same guard. Local prompt/answer/save/completion redraws still call `renderReview()` directly and must not reset origin. Normal non-review navigation clears it. Return renders the source, then focuses its original record without scrolling and restores document position. `state.historyFilter` keeps the real filter values through source returns; full `renderAuth()` clears filter/origin to avoid showing another account's search text, while session-expiry reauthentication retains unsaved review context. These values never enter API payloads.

Normal logged-in routes share the top navigation; immersive reviews hide it. The header review dropdown is removed; all six overview category cards remain the entry points from `TYPES`. `bindCommon()` mounts the real account/mobile DropdownMenu and binds guarded route buttons after each `shell()` render; a page rerender must rebind them.

Daily art is a static decorative composition inside `.daily-scene-art`: the eight existing prompt-specific images retain their ownership and side, with small paper/line/shape companions that have no focus, pointer, data or record behavior. Do not attach a hover tracker to the daily canvas. The overview uses a fixed-footprint CSS flip in `overview-entry.css` plus overviewBurst(), which returns a separate12-particle decorative sibling of the flipping face inside the original native button. Both layers remain aria-hidden/pointer-inert, and reduced motion hides particles while swapping faces instantly. Side-info helpers stay removed. Daily art must remain static and must not inherit that flip. The visible daily h2 may wrap a known keyword in a span created with text nodes/`textContent` for color emphasis, while its full plain text remains in the existing live status. Normalize legacy template titles to a string before searching or slicing for emphasis; a null/non-string title must never break prompt rendering.

These are current repository conventions. React is integrated through component islands; a full-page framework or router rewrite would be a separate explicit task.

`daily-calendar.js` retains pure date normalization and label helpers for the verification calendar shared by all six flows. `dailyCalendarModel(value,minimum,requestedMonth,locked,focusDate,today)` supplies a valid displayed month and focus date; the caller passes Beijing today. `app.js` owns `dailyVerificationCalendar()`, the stable hidden `data-simple=verifyDate` input, `renderDailyCalendar()` and `bindDailyCalendar()`. `showVerificationCalendar()` in `ui/surfaces.jsx` renders the actual shadcn/DayPicker Calendar, whose month state, day buttons and keyboard behavior have one owner. There is no parallel legacy key handler or system date popup. Empty values stay empty until explicit selection; month browsing does not dirty the record. Selection writes the original date field and dispatches its input event only when the value changes. Past editable selections open a usable current month without rewriting the original value; locked history disables navigation and keeps its original month even before the current minimum. The separate stage/calendar dialog keeps its own Calendar and record-opening rules.

`syncOverlayBackground()` is the shared owner of `#app.inert`, derived from an actual mounted modal or open stage Dialog. Both dialog roots and the singleton Sonner live outside `#app`; do not nest them under an inert application. Opening a child also makes `#right-rail` inert, closing it restores the parent while keeping the app inert, and closing the last dialog restores the app before returning focus. `prepareDialogContainer()` replaces an empty body-level modal mount for a new visit so a parent Radix `hideOthers` snapshot cannot hide the next child. Radix owns focus containment, Escape and scroll locking; the app supplies initial/return focus and busy/persistent close guards. Full `renderAuth()` dismisses the external rail, clears its open state and force-closes the modal before rendering auth; session-expiry reauthentication instead preserves the editor under its persistent dialog. Initialize Sonner before `init()` and keep live regions scoped to actual status content, never the entire app.

## Static asset cache contract

`shendu/server.mjs` serves non-HTML static assets with `Cache-Control: public, max-age=31536000, immutable`, while HTML is `no-cache`. When changing `shendu/public/app.js` or `styles.css`, change the matching `?v=` URL in `shendu/public/index.html` in the same commit. Component-source changes also require a rebuild and updated `public/ui/shadcn.js?v=` import in `app.js` plus `public/ui/shadcn.css?v=` reference in the entry HTML. Otherwise a returning browser can render new HTML or JS with stale runtime assets for up to a year. Verify the entry HTML and bridge import point to the current build before visual QA.

Authentication and connection surfaces use `legacy-surfaces.css` and existing local record art. `openModal()` opts ordinary confirmations into `.legacy-dialog` after parsing a detached template; it excludes explicit workspace/verification classes and the eight existing specialized operation-form IDs. Preserve title/description extraction, native fields, original binding order and Radix ownership. Full auth rendering disposes external overlays; persistent reauthentication retains the editor and its dirty state. Target-delete confirmation uses the same request ID and only deletes after explicit confirmation; pending work blocks duplicate/dismissal, and completion may update UI only if its original owner is still connected.

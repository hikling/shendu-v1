# Frontend Architecture

## Files and boundaries

- `shendu/public/index.html` provides the application, modal, and toast roots and loads `styles.css` and `app.js` directly. `shendu/package.json` has no frontend framework or bundler.
- `shendu/public/app.js` owns route state, HTML templates, API calls, and event binding. `shell(content)` renders the shared top navigation, main area, and right rail. `navigate(route)` selects the view.
- `shendu/public/styles.css` owns global tokens, page styles, and breakpoints. Local fonts live under `shendu/public/assets/fonts/`.

## Render and bind

Page functions return HTML strings. After DOM replacement, they attach listeners to the new nodes. `renderReview()` calls `shell(content)` then `bindReview()`; `shell()` calls `bindCommon()`. A rerender removes old listeners, so every new control needs a binding path.

The six review types share `TYPES`, `QUESTIONS`, `reviewToolbar()`, and `renderReview()`. Daily-specific content is split into `dailyEvidence()`, `dailyReflection()`, `dailyActionFields()`, and `dailyJournal()` in `app.js`. Extend the shared path for common behavior and the daily branch for daily-only behavior.

Daily review groups questions under `DAILY_STEPS` from `daily-flow.js`; `dailyPrompts(metricCount)` defines the actual screen order. `state.dailySection` tracks the01—04 group and `state.dailyPrompt` the current question (`sleep`, `energy`, `metric-N`, `risk`, `today`, `cause`, `action`, `ifCondition` (paired obstacle/response), `verifyDate`, `journal`). `dailyReviewHtml()` mounts all fields once; `showDailyPrompt()` changes `hidden` without replacing input nodes. `dailyPromptOwner(field)` maps ifThen to the combined ifCondition screen for traversal, redraw and exact-field error focus; both original inputs/payload keys remain mounted together. Use `dailyPromptIssues()` for current-question checks, `dailyStepIssues()` for final completion and `showDailyIssues()` to expose/focus the exact missing question. Evidence/cause/journal remain optional. `renderReview()` preservation options keep prompt/section/dirty through add/remove, save and completion. A first save changes null ID to a real ID and must not reset the flow. True record entry starts at intro; hidden questions still have values and participate in final validation.

Daily-only today/cause rows use dailyAnswerInputs() around the shared answerItemRow()/answerAddButton() markup. Native details keep all textareas mounted; dailyAnswerPreview() is escaped on render and assigned with textContent on edits. openDailyAnswer()/focusDailyAnswer() reveal one target before sizing/focus after add, remove or validation. Toggle alone does not mark dirty or save. Other five form variants retain their original HTML.

Daily uses a full art canvas for both intro and writing. `.daily-flow.daily-art-flow[data-daily-scene][data-daily-side][data-daily-current-prompt]` is the visual scene owner; its single `.daily-scene-art` contains the local transparent1254-square WebP `.daily-scene-image` variants generated with built-in imagegen; source PNG/prompt/manifest remain in assets/daily. The container is decorative, aria-hidden and pointer-inert. Scene state derives only from the current prompt; its side follows the real01—04group (right/left/right/left), never fabricated record content. `setDailyImmersive()` retains the shell/header cleanup role; daily intro now also hides the shared header, uses its own stage/date/exit controls without logo, and leaving daily restores the normal shell. Keep this exception local to daily. The daily header no longer renders headerBrandContent() or the daily divider; it keeps its unique current-group node, date and exit. Shared normal-page branding stays owned by headerBrandContent() and its existing guarded navigation. dailyIntroLines() splits only daily quote text at Chinese comma/full-stop, preserving punctuation and full text. Each phrase contains the same daily-glyph spans. The template supplies --daily-intro-columns from the longest code-point count with tracking allowance; scoped>=821px container units cap text size to the actual copy column, while phones retain natural wrapping. showDailyPrompt keeps the unique daily-current-group in the mounted header without a logo; focus transitions scroll that header instead of scrolling the editor past it, with a nearest start-button fallback in intro. `startDailyTypewriter()`/`cancelDailyTypewriter()` own the intro effect, preserve full-text geometry/semantics and cancel work on departure/replacement.

`statsHtml()` is owned by the shared stage/calendar dialog and renders once inside `rightRail()`. Review bodies must not call it. Its compact three-stat controls navigate through the existing guard after closing the parent dialog.

Routes are in-memory names such as `overview`, `daily`, `history`, `actions`, and `backup`. `boot()` opens `overview` after `refreshData()`. `renderOverview()` is the overview-only page; other page bodies retain their own render functions. `attemptNavigate()` guards unsaved input before moving between routes. Header, calendar, overview cards, and record-card handlers use that guard. Preserve it when adding navigation affordances.

The top navigation is shared by every logged-in route. `navItems()` filters the header review menu by `state.stage.showQuarter`, while the six overview category cards always come from all entries in `TYPES`. `bindCommon()` binds the header menus and route buttons after each `shell()` render; a page rerender must rebind them.

Daily artwork bursts are a local canvas-pointer enhancement: `bindDailyArtBurst()` tracks mouse entry on the active canvas while art/particles remain aria-hidden and pointer-inert. Bounds detection excludes real controls and held-button dragging. `cancelDailyArtBurst()` resets across prompts/motion changes; departure disposes canvas/window/media listeners. Effects do not write record/state fields, change focus or alter artwork choice. Keep one short outward burst per entry and suppress saved/system reduced motion and touch. `overviewBurst(className='overview-type-burst')` shares particle geometry while retaining identical default overview markup/behavior.

These are current repository conventions. A framework or router migration would be a separate explicit task.

`daily-calendar.js` owns the daily inline verification calendar's date-only model, keyboard date arithmetic and full Chinese labels: dailyCalendarModel(value,minimum,requestedMonth,locked,focusDate), dailyCalendarKeyDate(value,key,minimum,shift) and dailyCalendarDateLabel(value). The caller passes Beijing today. app.js owns dailyVerificationCalendar()/dailyCalendarHtml(), the stable hidden data-simple=verifyDate input, renderDailyCalendar() and delegated bindDailyCalendar(). Only the month subtree redraws; native table/day buttons provide interaction without an ARIA grid or popup. Empty values stay empty until explicit selection; month browsing does not dirty the record. Past editable selections open a usable current month without rewriting the original value, while locked history preserves its original month. The normalized model accepts a validated string representation without mutating supplied legacy data. Other five forms and the stage/calendar owner remain unchanged.

## Static asset cache contract

`shendu/server.mjs` serves non-HTML static assets with `Cache-Control: public, max-age=31536000, immutable`, while HTML is `no-cache`. When changing `shendu/public/app.js` or `styles.css`, change the matching `?v=` URL in `shendu/public/index.html` in the same commit. Otherwise a returning browser can render new HTML or JS with old cached CSS or JS for up to a year. Verify the entry HTML points to the edited assets before visual QA.
